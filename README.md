# APOLLO — облік поломок

Telegram-бот і Mini App на ASP.NET Core/.NET 10, React 19, TypeScript та EF Core. Основа — локальний `VPF_Algorithm_Bot`: структура сервера, перевірка Telegram initData, Bot API, режими Demo/Polling/Webhook та черга повідомлень. Це окремий застосунок; таблиці знаходяться у схемі `apollo`.

## Як працює

1. Працівник пише боту `/start` і відкриває форму.
2. Вибирає дільницю, зміну, працівника, APOLLO та каскад «частина → вузол → несправність».
3. Вказує виконання ремонту: **Самостійно / Залучення РМД / Залучення АСКВ / Залучення логістики**. Для залучення обов’язково відповідає, чи є резервне APOLLO: **Так / Ні**.
4. Надсилає заявку. Сервер зберігає її та починає відлік простою. Ручного введення тривалості й дати початку немає.
5. Автор отримує коротке підтвердження «Заявка прийнята». У групу APOLLO надходить повна заявка з кнопкою статусу.
6. Для РМД та АСКВ спочатку натискають «Почато ремонт» після прибуття, потім «Проблему вирішено». Для інших виконавців доступне одразу завершення. Група отримує подробиці, простій та час ремонту; автор — лише «Роботу відновлено». Повторні натискання не змінюють часові мітки.

Простій зберігається як точні часові мітки UTC; в експорті є секунди, у Telegram — повні хвилини (до хвилини: «менше 1 хв»). Журнал показує час Києва. Усі авторизовані користувачі бачать усі заявки та можуть змінювати їхній статус у журналі Mini App. У групі це може зробити будь-який учасник, що натиснув кнопку в повідомленні бота; дія записується з його Telegram ID.

## Довідники та доступ

У вкладці **«Адміністрування»** адміністратор додає, перейменовує, впорядковує, вимикає та видаляє варіанти всіх списків, включно з виконанням ремонту. Для варіанта ремонту є прапорець **«Запитувати про резервне APOLLO»**. Для кожної групи є системний пункт «Інше»; для обладнання він автоматично вибирає вкладені «Інше» та вимагає опис. Системний пункт залишається доступним. Прапорець «Показувати кнопку «Почато ремонт» перед завершенням» керує двоетапним ремонтом для нових заявок цього виконавця. Вимкнення частини або вузла перекриває його гілку у формі. Працівника можна обрати з підказок або ввести вручну.

Відправлені заявки зберігають копії назв: перейменування довідника не змінює історію. Фізичного видалення заявок чи довідника немає. Є журнал адміністративних змін через `/api/app/admin/audit`, CSV для Excel і стан черги Telegram у довідниках. Усі авторизовані користувачі бачать повний журнал та можуть експортувати CSV. Поза тестовим режимом API перевіряє підпис та строк дії Telegram initData. Тестовий режим відкриває форму без авторизації також на Azure.

Дані імпортовано з наданого Excel: 19 дільниць (№1–14, 22, 42, 43, 47, 49), 2 зміни, 3 працівники, 4 APOLLO, 3 частини, їх вузли й несправності. Додано гілку «Інше», інші несправності та 4 способи ремонту: 176 вихідних значень; додатково автоматично створюються відсутні «Інше» у кожній групі. Початкові назви збережено, обрізано зовнішні пробіли та прибрано один точний повтор у тому самому вузлі. JSON вбудовано в збірку; оригінальні вкладення для роботи сервера не потрібні. Довідник засівається один раз і надалі не перезаписує правки адміністратора. Міграція `CorrectSiteList` одноразово вимикає зайві початкові дільниці у вже створених SQL-базах; історія заявок залишається незмінною.

## Локальний запуск

Потрібні .NET 10 SDK та Node.js 22.12+ з npm.

```powershell
cd src/ApolloBreakdowns/ClientApp
npm ci
npm run build
cd ../../..
dotnet run --project src/ApolloBreakdowns
```

Адміністратор: `http://localhost:5179/miniapp/?demoUser=1`.
Оператор: `http://localhost:5179/miniapp/?demoUser=2`.

Профіль запуску встановлює Development; `appsettings.Development.json` вмикає Demo. У Demo база InMemory: дані зникають після перезапуску, Telegram не викликається. Чернетка форми живе у sessionStorage поточної вкладки. Для розробки React із перезавантаженням: `npm run dev` у ClientApp при запущеному сервері на 5179.

## Налаштування Azure App Service та SQL

Файлів GitHub Actions, Bicep, Docker чи інших файлів деплою немає — workflow створюється через ваш зв’язок Azure з GitHub. Публікується **`src/ApolloBreakdowns/ApolloBreakdowns.csproj`**. Команда `dotnet publish` цього проєкту сама виконує `npm ci` та `npm run build` і включає Mini App в результат публікації; на агенті збірки потрібен Node.js. Сервер віддає React за `/miniapp/`, API та статику з одного домену.

Задайте в Environment variables App Service:

| Назва | Значення |
|---|---|
| `ASPNETCORE_ENVIRONMENT` | `Production` |
| `Telegram__Mode` | `Webhook` |
| `Telegram__BotToken` | Токен **цього** бота з BotFather |
| `Telegram__PublicUrl` | `https://YOUR-APP.azurewebsites.net` без `/miniapp/` |
| `Telegram__WebhookSecret` | Секрет 1–256 символів: латиниця, цифри, `_`, `-` |
| `Telegram__GroupChatId` | Від’ємний ID групи APOLLO, наприклад `-1001234567890` |
| `Admin__TelegramIds__0` | Telegram ID адміністратора |
| `Admin__TelegramIds__1` | Другий адміністратор, якщо потрібен |
| `ConnectionStrings__BotDatabase` | SQL Server/Azure SQL connection string з `Encrypt=True` |
| `Telegram__AllowedUserIds__0` | Необов’язково: перший дозволений оператор |

Порожній `AllowedUserIds` дозволяє користуватися формою будь-якому користувачу Telegram, що відкрив її через бота; заповнений список обмежує операторів, адміністратори завжди мають доступ. Право завершення з повідомлення в налаштованій групі визначається участю у групі. Адміністративні Telegram ID та GroupChatId не є токенами, але мають відповідати вашому середовищу. Не додавайте токен або SQL-пароль у Git.

Під час запуску застосовуються EF Core migrations у схемі `apollo`, окрема історія `apollo.__EFMigrationsHistory`, далі засівається довідник під блокуванням міграцій. SQL-користувач повинен мати права на створення схеми й таблиць та їх подальше читання/зміну. Можна використати існуючу SQL Database з цією окремою схемою. Інші схеми ботів міграція не змінює. `/health` перевіряє роботу HTTP-сервера та повертає тип сховища (`memory` або `sql`) і стан тестового режиму. Якщо SQL не налаштовано, використовується пам’ять. Якщо ініціалізація SQL завершується помилкою або перевищує 20 секунд, застосунок переходить у тестовий режим із пам’яттю. Дані пам’яті зникають після перезапуску; SQL при цьому не видаляється.

Після налаштування бот автоматично реєструє webhook `https://YOUR-APP.azurewebsites.net/api/telegram/webhook` із секретним заголовком і кнопку меню Mini App. Додайте бота в групу APOLLO та дозвольте надсилати повідомлення. Для отримання ID групи адміністратор може написати `/chatid@ІмяВашогоБота` у групі (GroupChatId необов’язковий для запуску; задайте фактичний ID, щоб увімкнути групові повідомлення). Користувачам потрібно один раз відкрити особистий чат із ботом і натиснути Start, щоб він міг надсилати їм особисті підтвердження. У BotFather можна додатково налаштувати Main Mini App на `https://YOUR-APP.azurewebsites.net/miniapp/`.

Для роботи фонової черги App Service має залишатися активним: увімкніть Always On на тарифі, який це підтримує. Webhook працює на декількох інстансах: завдання черги мають SQL lease та контроль версій. Polling — лише для одного локального інстансу з HTTPS-адресою Mini App, режим `Polling` видаляє webhook цього бота.

Повідомлення зберігаються разом із заявкою/завершенням в одній SQL-транзакції. За помилки Telegram повторюються з паузою до години; групова доставка не залежить від того, чи дозволені особисті повідомлення автору. Доставка щонайменше один раз: при збої між успішною відповіддю Telegram та фіксацією в SQL повідомлення може повторитися; сама заявка й час завершення залишаться єдиними.

## Перевірки

```powershell
dotnet run --project tests/ApolloBreakdowns.Tests
cd src/ApolloBreakdowns/ClientApp
npm test
npm run build
cd ../../..
pwsh -NoProfile -File scripts/smoke.ps1
dotnet publish src/ApolloBreakdowns -c Release -o .test-output/publish
```

Domain-тести використовують SQLite для перевірки справжнього rollback транзакції, унікальності, повторного й конкурентного завершення. Bot API перевіряється транспортом-заглушкою: повідомлення у Telegram не надсилаються. Smoke запускає локальний Demo-сервер і перевіряє API, доступи, каталог, збереження й завершення заявок. Реальні Telegram-група, Azure SQL та хостинг потребують перевірки після налаштування середовища.

Оновлення EF Core migrations: `dotnet tool install dotnet-ef --version 10.0.10 --tool-path .tools`, потім `.tools/dotnet-ef migrations add NAME --project src/ApolloBreakdowns --output-dir Data/Migrations`. Для повторного імпорту вихідного Excel у seed JSON: `python scripts/import_catalog.py PATH.xlsx` (це змінює початковий seed для нової БД; не оновлює вже засіяні бази).

## Запуск без налаштувань

Для тестування на Azure встановіть `App__TestMode=true`, збережіть і відкрийте `/miniapp/` прямо в браузері. Чат, адміністратори, SQL, токен та webhook не потрібні. Доступні форма, історія, завершення простою та редагування довідників. Дані тимчасові, повідомлення не надсилаються. Щоб повернути робочий режим, встановіть `App__TestMode=false` і налаштуйте інтеграції.

Без токена також автоматично вмикається тестовий режим. У робочому режимі група й список адміністраторів необов’язкові: без групи повідомлення отримує автор заявки, без адміністраторів приховано керування довідниками. Без коректної HTTPS-адреси або webhook-секрету бот використовує polling. Секрет підтримує 1–256 латинських літер, цифр, `_` та `-`.

## Стійкість до помилок

HTTP-сервер стартує незалежно від ініціалізації сховища. Міграції та засівання виконуються у фоновій задачі; до готовності сховища API повертає 503 з Retry-After, статична форма та `/health` доступні. Форма повторює початкове завантаження через 3 секунди після 503. `/health` повертає `storageReady`, а `/health/ready` окремо перевіряє готовність сховища (503 при недоступності).

Фонові задачі мають зовнішній захист від винятків із повторним запуском через 15 секунд. Помилка фонової інтеграції не зупиняє HTTP-сервер. Помилки запитів ізольовані; помилка SQL повертає 503. При втраті SQL під час роботи застосунок не перемикає робочий журнал у порожню пам’ять: повторний запит знову спробує SQL. Автоматичне тимчасове сховище застосовується при початковій ініціалізації, як описано вище.

Ці механізми захищають від оброблюваних помилок застосунку та інтеграцій. Вони не можуть заборонити Azure зупинити контейнер, скасувати платформне блокування або відновити процес після вичерпання пам’яті.

## Користувачі, ремонт, нагадування та експорт

Користувачі записуються після перевіреного входу в Mini App, повідомлення боту або callback-кнопки; зберігаються ID, ім’я та перша/остання активність. Адміністратор надає й відкликає права у вкладці «Адміністрування». Початкові `Admin__TelegramIds` застосовуються при першому встановленні ролі; далі роль зберігається у базі. Власні права відкликати не можна. Автори попередніх заявок переносяться в список користувачів міграцією. Користувачів, які раніше лише відкривали бота й не залишили записів у базі, можна зафіксувати після наступного входу.

Для РМД/АСКВ фіксуються `RepairStartedAt` і `RepairStartedByUserId`. Простій = створення → завершення; ремонт = початок ремонту → завершення. До натискання початку завершити двоетапну заявку не можна. Для інших служб ремонтний інтервал не вигадується. Прапорець у довіднику виконавців задає цей етап для нових заявок; незавершені попередні заявки РМД/АСКВ отримують його міграцією.

Адміністратор створює, редагує, вимикає й видаляє кілька щоденних розсилок за часом `Europe/Kyiv` (з переходом на літній/зимовий час). Фоновий процес перевіряє розклад кожні 30 секунд; вікно надолуження після короткого простою — 10 хвилин. Якщо відкритих заявок немає, повідомлення не надсилається; перед повторною доставкою стан перевіряється знову. Список містить до 15 найстаріших відкритих заявок і загальну кількість. Потрібен запущений застосунок: сон або зупинка App Service унеможливлюють фонову відправку. У Demo повідомлення не відправляються.

CSV доступний усім у журналі: у Telegram кнопка надсилає файл через `sendDocument` в особистий чат користувача; у звичайному браузері завантажує файл. Потрібно раніше натиснути Start у боті. CSV містить UTF-8 BOM, захист від Excel-формул, усю історію, початок ремонту й окремі тривалості простою/ремонту. Звичайний GET `/api/app/export` потребує автентифікації, POST `/api/app/export/send` надсилає документ; попередній адмін-маршрут збережено.

Видалення довідника приховує його та вкладені пункти, зберігаючи знімки назв у заявках та аудит. Міграція `UsersRepairReminders` додає таблиці/поля без видалення історії. Перед оновленням робочої SQL-бази використайте її звичайне резервне копіювання.
